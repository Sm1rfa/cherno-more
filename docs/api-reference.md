# Football data: schema, providers, caching

How the app gets fixtures, standings, squad, history, and news for FC Cherno More Varna.

```
src/api/
  football.ts             orchestrator — what components import
  cache.ts                localStorage cache-aside helper
  fixtureState.ts          shared fixture-status classifier (all providers map onto this)
  constants.ts             OUR_TEAM_ID — the one canonical "us" id
  providers/
    sportscore.ts           primary live provider (fixtures + standings)
    goalBg.ts                secondary live provider, used once configured
    manual.ts                last-resort fallback — reads public/data/*.json at runtime
    history.ts               reads public/data/history/*.json at runtime
public/data/               hand-edited JSON — see public/data/README.md
public/data/history/       generated by scripts/build-history.mjs, not hand-edited
docs/sportscore-openapi.yaml  SportScore's own OpenAPI spec, for reference
src/types/football.ts      canonical Fixture / Standing types
src/types/squad.ts         canonical SquadPlayer / SquadCoach types
src/types/history.ts       canonical SeasonHistory / HistoryMatch / HistoryEvent types
```

## Why three fixtures/standings sources

This app originally planned to use **api-football.com** (api-sports.io) as the primary data source. In practice, api-football's **free plan only serves seasons 2022–2024** — confirmed directly from the API's own error response. For a fan app tracking the *current* season, that's a non-starter; it was removed entirely. See [`plans/2026-08-api-football-migration.md`](./plans/2026-08-api-football-migration.md) and [`plans/2026-08-goalbg-only-pivot.md`](./plans/2026-08-goalbg-only-pivot.md).

**SportScore** (sportscore.com) is the current primary: free, no API key, CORS-enabled (so the browser calls it directly), and verified accurate against data we'd already parsed by hand — every number matched. Its one condition is attribution (see below), not a request quota, so it's the natural default rather than something to save for later. **api.goal.bg** is the secondary: Bulgaria-specific and free, but its key isn't self-serve (email api@bgclubs.eu) — it's used once `VITE_GOALBG_KEY` is set, ahead of the manual dataset but behind SportScore. **The manual JSON dataset** (`public/data/`) is the last resort if both live sources fail, and squad's only source, live or otherwise — neither API has player/roster data.

## Canonical types

```ts
// src/types/football.ts
Fixture {
  fixture: { id, date, timeTBD?, status: { short, elapsed } }
  league:  { name, round }
  teams:   { home: {id, name, logo, winner}, away: {...} }
  goals:   { home, away }
}

Standing {
  rank
  team: { id, name, logo }
  points, goalsDiff
  all: { played, win, draw, lose, goals: { for, against } }
  form            // always null — none of the sources provide recent-form data
  description     // human zone label, e.g. "Title Play-offs" (SportScore) or "Първа група (1-4 място)" (manual)
  color?          // explicit zone color, when the provider gives one (SportScore's promo_color) — else derived from `description` keywords
}

// src/types/squad.ts
SquadPlayer {
  id, name, nameLatin?, number, position: 'вратар'|'защитник'|'полузащитник'|'нападател',
  birthYear?, nationality?, photo?, captain?, goals?, assists?, yellowCards?, redCards?
}
SquadCoach { id, name, role? }
```

`fixture.status.short` is always one of `FINISHED` / `LIVE` / `CANCELLED` / `SCHEDULED` (or a couple of goal.bg-specific synonyms like `NOT_SCHEDULED`/`POSTPONED`) — every provider maps its own native status vocabulary onto this set before returning a `Fixture`, so there's exactly one classifier: `fixtureState(short)` in `src/api/fixtureState.ts` (re-exported from `football.ts`), returning `'upcoming' | 'live' | 'finished' | 'cancelled'`. SportScore is the only source that can actually produce `'live'` — goal.bg and the manual dataset have no in-play data, so it's modeled for them but never produced. `timeTBD: true` means the kickoff time isn't announced yet — `Fixtures.tsx` shows "Часът предстои" instead of a fake time; SportScore always gives a concrete time (even for far-out rounds, likely a provisional slot), so `timeTBD` is only ever set by the manual dataset.

**Team identity across sources:** `team.id` is always a plain number, but each provider gets there differently. goal.bg's ids look like `"12345-111"` (numeric prefix used directly). SportScore and the manual dataset only have team *names* (strings) and each assigns a stable id the first time a name is seen in a page load. Either way, "us" is always `OUR_TEAM_ID` from `src/api/constants.ts` — goal.bg remaps whichever id matches your configured `VITE_GOALBG_TEAM_ID` onto it; SportScore hardcodes the mapping for `"Cherno More Varna"`; the manual dataset hardcodes it for `"Черно море"`. Components only ever compare `team.id === TEAM_ID` (re-exported from `football.ts`) and don't need to know which source answered.

Team **names** differ by source too (SportScore/api-football-style are English, goal.bg/manual are Bulgarian) — `src/utils/teamNames.ts` is a lookup table translating known Latin variants (including SportScore's exact strings, e.g. `"FC Dunav Ruse"`, `"FK Septemvri Sofia"`) to Bulgarian; anything unrecognized just passes through unchanged. `Standings.tsx` also translates SportScore's English zone names (`"Title Play-offs"` etc.) via its own small `ZONE_LABEL_BG` map, same passthrough-if-unknown behavior.

## SportScore (primary)

- Base URL: `https://sportscore.com`, no auth, CORS-open, ~10,000 req/day/IP, 60s edge cache.
- Full spec: [`sportscore-openapi.yaml`](./sportscore-openapi.yaml) (added to the repo for reference — see also https://sportscore.com/developers/).
- **Attribution is the price of the free tier, not optional**: their terms require *"a visible 'Powered by SportScore' link... with `rel="dofollow"` — `nofollow`, `ugc`, and `sponsored` are not acceptable substitutes"* on every screen that renders their data. That's implemented once, app-wide, in `Header.tsx` (rendered on every tab) rather than per-tab. `rel="dofollow"` isn't a real HTML spec value (only `nofollow` is standardized) but it's what their terms ask for literally, so that's what's in the markup.

| Data | Endpoint used | Notes |
|---|---|---|
| Fixtures | `/api/v1/team/?sport=football&slug=cherno-more-varna&limit=50` | Returns *all* competitions (league + friendlies) — filtered to `competition === "Bulgarian First League"`. No round number in the response; since Cherno More plays exactly once per round in a single round-robin, chronological order among league matches doubles as the round number. |
| Standings | `/api/v1/standings/?sport=football&slug=bulgarian-first-league` | Gives `promo_color`/`promo_name` per row directly — real zone color/label, no guessing needed (unlike the other two sources). |

`docs/sportscore-openapi.yaml` documents a few more endpoints not currently wired up (`/api/v1/h2h/`, `/api/v1/search/`, `/api/v1/topscorers/`, single match/player lookups) — no full squad/roster endpoint exists, so `squad.json` stays manual regardless.

### Live match detail (`/api/widget/match/`)

SportScore-only — bypasses `football.ts`'s provider fallback entirely, since neither goal.bg nor the manual dataset has anything equivalent. `fetchMatchDetail(slug, kickoff)` in `providers/sportscore.ts` hits `/api/widget/match/?sport=football&slug=...`; every `Fixture` from SportScore carries a `slug`, taken from the match's own `url` (`/football/match/<slug>/<id>/`) and only derived from team names as a last resort.

**A slug names the pairing, not the game.** Every meeting of the same two teams shares one slug, and the widget accepts no match id. Confirmed 2026-10-04: the 2026-10-11 Levski match's slug answered with the finished 2026-03-21 meeting, and round 6 (vs Dunav) answered with a September friendly. So `fetchMatchDetail` checks the returned `match.time` against the expected kickoff (±12h). On a mismatch it falls back to `/api/v1/fixtures/?date=<UTC date>&team=cherno-more-varna`, which is always the right game but carries only score/status — `incidents`/`stats`/`lineups` come back empty. Whether the widget switches to the right game once it's live is unknown; the guard covers either case. `public/push/check-match.php` has the same guard (it then announces goals as score changes, with no scorer), and keys its state/log files by slug **+ kickoff date** so a second-half rematch doesn't inherit the first meeting's "already finished" state.

Confirmed shape live against two real matches (pre-kickoff: empty; genuinely live: full data) — not documented in `sportscore-openapi.yaml` beyond "match detail envelope":

```ts
MatchDetail.match {
  home, away, home_logo, away_logo, home_score, away_score, home_ht_score, away_ht_score,
  status, status_text, time, competition, live_minute,
  incidents: [{ time, type, type_id, side: 'home'|'away', player,
                 is_goal?, is_card?, is_sub?, player_in?, player_out?, home_score?, away_score? }],
  stats: [{ label, home, away, home_pct, away_pct, suffix }],
  lineups: { home_formation, away_formation, home_coach, away_coach, confirmed,
             home_xi, home_subs, away_xi, away_subs: [{ name, number, position, captain, rating }] } | null,
}
```

`src/hooks/useLiveMatch.ts` polls this every 30s, but only while the fixture is inside its live window (10 min before kickoff to ~3h after — the frontend's own timing, kept in sync by hand with `public/push/config.php`'s identical window on the backend). Outside that window it's a no-op timer, not a real request — client-side polling like this is safe against the ~10,000 req/day/IP quota because each visiting browser polls with its own IP, never a shared budget. `Fixtures.tsx` renders the live score/incidents from this (falling back to the coarser cached fixture list until the first poll lands) plus a separate collapsible lineups section once `lineups.confirmed` is true — that section is **not** a click target on the match card itself, a known UX gap (see `docs/plans/2026-08-live-match-and-push.md`).

On full-time, the hook calls `cache.invalidate('standings')`/`invalidate('fixtures')` so those tabs' next fetch isn't stuck on their 60-min/10-min TTL.

**Player names are Latin-only from SportScore** — no free source gives Cyrillic names for arbitrary players, so opponents' names stay as SportScore renders them. Cherno More's own players, though, are resolved to the Cyrillic names already hand-maintained in `squad.json`, via a two-step join that needs no new data entry: an incident's Latin `player` name is matched against that match's own lineup entries (`home_xi`/`home_subs`/`away_xi`/`away_subs`, same match, same side) to get a jersey `number`, then `squad.json`'s `number -> name` (built once per page load in `Fixtures.tsx`) resolves that to Cyrillic. Falls back to the Latin name at either step (lineups not yet confirmed, no match found, no squad entry for that number) rather than guessing. `resolveOurPlayerName()` in `Fixtures.tsx`.

## api.goal.bg v2 (secondary — active once `VITE_GOALBG_KEY` is set)

- Base URL: `https://api.goal.bg/v2`
- Auth: header `X-GOALBG-Key: <VITE_GOALBG_KEY>` — **not self-serve**, request one by emailing api@bgclubs.eu.
- Envelope: `{ GET, parameters, count, response }`
- Enforces its own rate limit (`X-RateLimit-*` response headers) — another reason the cache matters.

| Data | Endpoint | Notes |
|---|---|---|
| Fixtures | `/matches.json?tournament_id={VITE_GOALBG_TOURNAMENT_ID}&team_id={VITE_GOALBG_TEAM_ID}` | `date`+`time` have no timezone — parsed as local browser time, fine for a Bulgaria-only audience but not exact across DST changes |
| Standings | `/standings.json?tournament_id={VITE_GOALBG_TOURNAMENT_ID}` | response is `[{ standings: [...] }]`; numeric fields arrive as strings and are parsed |
| Club search | `/clubs.json?name=` | one-off lookup to find a `club_id`, no UI for it (the old Discovery tab that had one is gone — see the News section below) |
| Teams by club | `/teams.json?club_id=` | one-off lookup to get the exact `VITE_GOALBG_TEAM_ID` string |
| Tournaments | `/tournaments.json` | one-off lookup to confirm `VITE_GOALBG_TOURNAMENT_ID` |

## Manual data (`public/data/*.json` + `src/api/providers/manual.ts`)

Fixtures, standings, and squad are hand-edited JSON files served as plain static assets from `public/data/` — **fetched at runtime**, not imported/bundled into the JS. That's the point: editing a value and redeploying just that file is enough, no app rebuild required. Full field-by-field format is in [`public/data/README.md`](../public/data/README.md) — that's the file to open when you actually want to edit something; this section explains the *why* and how it wires into the rest of the app.

**Provenance**: fixtures/standings were bootstrapped from a season-summary page copied by hand from bulgarian-football.com into a local `.txt` file and handed over to be parsed — a human reading a public page and choosing to share it, categorically different from a bot scraping a site that opted out of exactly that (see [`plans/2026-08-data-sources-declined.md`](./plans/2026-08-data-sources-declined.md)). Squad's initial roster came from `chernomorepfc.bg/otborat/`, permitted by that site's robots.txt.

**Why team names, not ids, in the JSON**: `fixtures.json`/`standings.json` refer to teams by their plain Bulgarian name string (e.g. `"Черно море"`, `"ФК ЦСКА 1948 (София)"`) rather than a numeric id with a separate lookup table — hand-editing JSON is easier without needing to cross-reference ids. `manual.ts` assigns numeric ids internally (see "Team identity" above) so the rest of the app's type system doesn't need to know the difference.

**Goals in `squad.json` were first derived from the season-summary text** (its `[minute' Scorer]` breakdown per match, cross-checked against `standings.json`'s `goalsFor`), then **assists and cards were filled in from a second, independent source**: the user's own Python scraper (`bg-ft-parser`, output at a local path outside this repo) parses full match reports off bulgarian-football.com — lineups, substitutions, goals *with assists*, cards, referee, attendance — for the current season and, notably, **18 full seasons back to 2008/09**. Its current-season per-player stat file (`cherno_more_stats_current.json`) is where `squad.json`'s `assists`/`yellowCards` values came from, after manually cross-referencing against known player names.

That file has a real parsing bug worth knowing about if it's used again: bench/substitute text sometimes bleeds into a `name` field, producing garbled entries like `"Кристиан Томов - 5.Лусиано Скуадроне"` or bare numbers as names — about half of its ~53 "players" for the current season are such artifacts, not real distinct people. Only entries that exactly matched a known `squad.json` player by name were trusted; everything else was ignored. One real discrepancy surfaced this way: the parser has Петър Андреев wearing **#18** in matchday squads, while `chernomorepfc.bg`'s own player page said **#2**. SportScore's lineups also show **#18** in all 6 matches he's listed in, so it was changed to `18` on 2026-10-04 (the live-lineup Cyrillic name resolution joins on number, so `2` meant his name never resolved).

The historical seasons (`cherno_more_matches_YYYY_YYYY.json`, `cherno_more_stats_YYYY_YYYY.json`, plus `cherno_more_all_matches.json`/`cherno_more_all_time_stats.json`) aren't wired into the app yet — see [`plans/2026-08-history-data-shaping.md`](./plans/2026-08-history-data-shaping.md) for what's actually in them and the open design question of how (or whether) to expose them.

## Orchestration (`src/api/football.ts`)

`fetchFixtures()`/`fetchStandings()` try each configured source in priority order and use the first that succeeds, all behind one cache entry:

```
fetchFixtures()/fetchStandings() -> cache.getOrFetch(key, ttl, () => withFallback(
                                        sportscore.fetchX,
                                        ...(goalBg.hasKey() ? [goalBg.fetchX] : []),
                                        manual.fetchX,
                                      ))
fetchSquad()                     -> cache.getOrFetch('squad', ttl, manual.fetchSquad)
```

`withFallback` just tries each function in order and returns the first success, throwing the *last* error only if all of them fail. goal.bg is skipped entirely from the list when no key is set, rather than attempted and expected to fail.

`fetchFixturesMeta()`/`fetchStandingsMeta()` (also re-exported from `football.ts`) fetch just the `updatedAt` field from the manual JSON specifically, uncached — used for the small footer each tab shows. These always reflect the manual dataset, not whichever source actually answered the main request (worth knowing, not worth solving today, since the manual dataset is the meaningful "last updated by a human" signal regardless).

## Caching (`src/api/cache.ts`)

Cache-aside, backed by `localStorage` (survives full reloads and Vite HMR):

```ts
getOrFetch(key, ttlMs, fetcher, { force? }): Promise<T>
```

1. Fresh cache entry (age < ttlMs) and `force` not set → return it, **no network call**.
2. Otherwise call `fetcher()`. On success, store `{ data, fetchedAt: Date.now() }` under `cache:v1:<key>` and return it.
3. `fetcher()` throws → if *any* cached entry exists (even expired), return that as a last resort; otherwise rethrow.

Default TTLs (`CACHE_TTL` in `cache.ts`): fixtures 10 min, standings 60 min, squad 15 min (short — deliberately, since `squad.json` can now be updated independently of an app deploy, and a long TTL would blunt that), history 24h (long — it only changes when `npm run build:history` is rerun).

Each tab has a small "↻" button that calls the fetch with `force: true`, bypassing the TTL on demand. `clearCache()` wipes everything; no UI wires it up right now (the Discovery tab that used to is gone — see the News section below), so call it from the browser console (`import('/src/api/cache.ts').then(m => m.clearCache())` in a dev session) if needed.

The PWA service worker (`vite.config.ts`) also runs a separate `NetworkFirst` runtime cache for `/data/*.json` — deliberately **not** part of the build-time precache manifest, so it never gets locked to a specific build's file hash. That's what actually makes "edit a JSON file, redeploy just that file" work for already-installed users too: the next successful fetch picks up the change, with the runtime cache only as an offline fallback.

## Match archive / History tab (`public/data/history/*.json` + `scripts/build-history.mjs`)

18 seasons (2008/09–2025/26) plus the current one, built from the user's own local Python scraper output (`bg-ft-parser`, not part of this repo, not web-fetched) via `npm run build:history` into `public/data/history/{season}.json` + an `index.json`. Same runtime-fetch pattern as the rest of `public/data/` — see `src/api/providers/history.ts`, `src/types/history.ts`, `src/components/History.tsx`.

**Deliberately excludes starting-XI/bench lineups.** Measured the source data before building on it: the event timeline (goals w/ assists, cards, substitutions) had zero corrupted entries in a full season checked, but the raw lineup rosters had 36–43% of entries with bench text bled into the player-name field (a real bug in the scraper, e.g. `"Кристиан Томов - 5.Лусиано Скуадроне"` as one "player") — too pervasive to filter around without showing visibly incomplete lineups. The archive is built entirely from what's clean: match results, venue/referee/attendance/weather, the event timeline, and each season's top-scorer/assister/most-carded leaderboards (also clean). Full writeup: [`plans/2026-08-history-data-shaping.md`](./plans/2026-08-history-data-shaping.md).

Goal events carry no direct "was this us" flag in the source, so `build-history.mjs` derives it from the running home/away score included on each goal (whichever side's number just went up), rather than trying to match scorer names against the (unreliable) lineup data — verified against several real matches, including a 2008/09 one, and it tracked correctly throughout.

Rerun `npm run build:history` whenever the scraper output changes (new season, or if the lineup-parsing bug ever gets fixed at the source — worth revisiting then, since a full lineup view would be a natural addition once that data is trustworthy).

## News (`public/data/news.json` + `public/push/fetch-news.php` / `scripts/fetch-news.mjs`)

The old Discovery/setup tab was replaced with a News tab, fed by two RSS feeds merged and sorted newest-first:

- `https://chernomorepfc.bg/feed/` — the official club's own WordPress feed, unrestricted robots.txt, every item kept.
- `https://www.varna24.bg/rss.php?cat=3` — general Varna sports news, filtered down to items mentioning "черно море" (it covers all local sports, not just this club).

On the varna24.bg feed specifically: its robots.txt disallows `ClaudeBot` sitewide (Cloudflare's standard AI-crawler block-list toggle — also covers GPTBot, Google-Extended, CCBot, etc.), which sits in tension with the fact that an RSS feed is itself a mechanism the site built for automated syndication, with an explicit `Content-Signal: ai-train=no, use=reference` note alongside it. That's a genuine judgment call rather than a bright line either way; see [`plans/2026-08-data-sources-declined.md`](./plans/2026-08-data-sources-declined.md) for the fuller reasoning — the project's call was to use it.

Each item carries a `source` field (shown on its card) so it's clear which feed it came from. It's a snapshot, not a live fetch, for two unrelated reasons: neither feed sends CORS headers, so a browser `fetch()` would be blocked in production regardless of source, and hitting someone's feed on every page load instead of periodically would be rude either way. On the server, `public/push/fetch-news.php` (cron, every 30 min) rewrites `data/news.json` in place, so the deployed snapshot stays fresh without a rebuild. If one feed fails, that source's previous items are kept; if all fail, the file is left untouched. `scripts/fetch-news.mjs` (`npm run fetch:news`) is the same logic for local use. The two are kept in sync by hand, and were verified to produce byte-identical output on 2026-10-04. `News.tsx` fetches the resulting file at runtime, same as the other manual data.

Losing Discovery also means losing its goal.bg club/team-id search UI. Not a real loss — that was only ever needed once, to find `VITE_GOALBG_TEAM_ID`; ask for that lookup directly (a one-off request against `/clubs.json`) once a goal.bg key exists, instead of keeping a whole tab around for a single setup step.

## Push notifications (`public/push/`, PHP + cron)

Ships into `dist/push/` via Vite's normal `public/` copy — no separate deploy step. Full narrative/why in [`plans/2026-08-live-match-and-push.md`](./plans/2026-08-live-match-and-push.md); this is the "how it works now" summary.

```
public/push/
  check-match.php   cron entry point — run "Once Per Minute", self-gates (see below)
  subscribe.php     browser POSTs {action, subscription} here to add/remove a push subscriber
  config.php        VAPID keypair + SportScore/window constants — blocked from direct HTTP access
  common.php        shared JSON-file helpers + fetchJsonUrl() (returns null, never throws, on failure)
  vendor/           minishlink/web-push + guzzlehttp/guzzle, vendored (no server-side Composer needed)
  data/             subscriptions.json, today-fixture.json, match-state-{slug}.json — .htaccess-blocked
  status.php        diagnostics: cron's absolute path, PHP version, writability — delete once confirmed
```

`check-match.php` is designed to run unconditionally every minute, forever — it self-gates so that's cheap: a once-daily-refreshed local cache of "today's next fixture" avoids hitting SportScore at all on non-match days, and even with a fixture cached, it only calls `/api/widget/match/` when `now` is inside the same live window `useLiveMatch.ts` uses on the frontend (10 min pre-kickoff, ~3h cap after). It diffs `incidents`/`status` against a per-match state file and sends push for kickoff, each new goal/card (substitutions excluded), and full-time.

**Requires PHP ≥ 8.2** (the web-push library's requirement) — a generic cron PHP binary path may point somewhere older than the version actually needed; `status.php` reports the real version once deployed.

The frontend half — `src/push.ts` (`subscribeToPush()`/`unsubscribeFromPush()`), `src/sw.ts`'s `push`/`notificationclick` handlers, `src/components/NotificationToggle.tsx` in `Header.tsx` — is built and deployed but not yet exercised against a real goal/push send; the cron/backend side has been confirmed working live (correct fixture selection, correct window gating, a real VAPID-signed send attempt) but end-to-end delivery to a real subscribed device hasn't been observed yet.

**iOS note**: push only works on iOS Safari for a PWA added to the home screen (iOS 16.4+) — a plain Safari tab visit never receives push there, regardless of permission state. Android/Chrome works from a normal browser visit.

## Known limitations

- **Client-side keys**: `VITE_*` vars are bundled into the shipped JS and visible to anyone opening devtools. (SportScore needs no key at all, which sidesteps this entirely for the primary source.) A backend proxy would fix it for goal.bg but is out of scope for now.
- **goal.bg timezone**: match `date`+`time` have no offset; parsed as local browser time.
- **SportScore's far-future kickoff times may be provisional**: it returns a concrete time for every match, even rounds where bulgarian-football.com itself hadn't announced one yet — likely a provisional slot subject to change, not confirmed. Taken at face value since the source has otherwise been accurate; no separate "unconfirmed" flag is surfaced.
- **Live match state depends entirely on SportScore**: goal.bg and the manual dataset have no in-play data at all.
- **Squad doesn't refresh itself**: no free API has player/roster data, so it's manual forever — goes stale the moment a transfer happens and nobody's updated `squad.json`, with only the `updatedAt` label as a hint.
- **No per-player, per-match stats going forward** (assists, cards broken out by game): the one site that had this, `bulgarian-football.com`, explicitly disallows `ClaudeBot` in its `robots.txt` — see [`plans/2026-08-data-sources-declined.md`](./plans/2026-08-data-sources-declined.md). Goals so far were derivable from the season-summary page's match-by-match scorer lines, but that only covers what's in a page pasted by hand — assists/cards need another source or manual entry from box scores read yourself.
- **Lineups aren't a click target on the match card**: the "Стартови състави" section in `Fixtures.tsx` appears automatically above the fixture list once available, not on tapping the card itself — doesn't match the original ask, unresolved.
- **~30s is close to the practical live-update ceiling for free**: SportScore's own API is edge-cached 60s at their end, so polling faster gets no fresher data, just spends quota. Flashscore/Livescore-level speed needs a paid low-latency feed.

Not built yet — deferred until a working `VITE_GOALBG_KEY` is available to test against.
